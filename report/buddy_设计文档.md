## 1. 设计目标与约束

### 1.1 任务要求

Challenge 要求：Buddy System 把系统中的可用存储空间划分为存储块（Block）进行管理，每个存储块的大小必须是 2 的 n 次幂，即 1, 2, 4, 8, 16, 32, 64, 128…；参考伙伴分配器的一个极简实现，在 ucore 中实现 buddy system 分配算法；要求有比较充分的测试用例说明实现的正确性；需要有设计文档（即本文）。

### 1.2 运行环境

- RISC-V 64 位教学内核（ucore 风格），QEMU 模拟，DRAM 128 MiB，物理基址 `0x80000000`
- 页大小 4096 字节；页描述符数组 `pages[]` 由 `page_init()` 建立
- 单核、串行调用：无并发场景，不需要锁
- 128 MiB / 4 KiB = 32768 页，因此阶数上限为 15（`2^15 = 32768` 页）

### 1.3 工程约束

1. 完整实现 `struct pmm_manager` 六个回调：`init`、`init_memmap`、`alloc_pages`、`free_pages`、`nr_free_pages`、`check`
2. 不修改公共 `struct Page` 定义与 `pmm_manager` 接口
3. 不破坏已有模块：物理内存初始化、First-Fit、Best-Fit、SLUB、公共接口与评分工具
4. 初始化不能依赖任何分配服务：`init()` 运行时 `page_init()` 尚未执行、SLUB 未建立，宿主 `malloc/free` 不可用
5. 兼容 SLUB 的使用方式：`alloc_pages(n)` 取得连续页后，按同一原始 `n` 调用 `free_pages(base, n)` 归还

### 1.4 主动选择的接口契约

| 约定       | 内容                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ |
| 分配取整   | `alloc_pages(n)`（`n>0`）实际分配最小的满足 `2^k ≥ n` 的二次幂页数                                                       |
| 配对释放   | `free_pages(base, n)` 中 `n` 是原始申请页数，归还整个实际块：`alloc_pages(3)` 实占 4 页，`free_pages(base, 3)` 归还 4 页 |
| 计数语义   | 空闲页计数按实际块大小（`2^k`）变化，不按 `n`                                                                            |
| 失败路径   | `n==0`、`n>32768`、空闲总量不足、无可用阶块时返回 `NULL`，且不改变任何管理状态                                           |
| 明确不支持 | 内部偏移释放、部分释放、重复释放、非法指针（不在本任务契约内）                                                           |

## 2. 总体结构

### 2.1 模块组成

| 文件             | 职责                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| `buddy_pmm.c`    | 分配器本体：管理状态、六个回调、结构自检；另含受 `PMM_USE_BUDDY` 保护的测试挂钩（状态切换入口） |
| `buddy_pmm.h`    | 常量（`BUDDY_MAX_ORDER=15`、`BUDDY_MAX_PAGES=32768`）与 `buddy_pmm_manager` 声明                |
| `buddy_test.c/h` | 八组行为测试（测试设计详见实验报告 4.2.3 第二阶段）                                             |

### 2.2 生命周期与数据流

```text
pmm_init()
 ├─ init_pmm_manager()   #ifdef PMM_USE_BUDDY → buddy_pmm_manager，否则 best_fit_pmm_manager
 ├─ page_init()          探测 DRAM、建立 pages[]、划定保留区
 ├─ buddy_init()         清零集中状态、初始化 16 条链表（不访问页描述符）
 ├─ buddy_init_memmap()  登记空闲区：清标志 → 逐段拆成对齐二次幂块 → 尝试合并
 └─ check                结构自检 →（PMM_USE_BUDDY 下）运行 buddy_test() → 再次结构自检
```

分配数据流：请求 `n` → 范围检查与取整 → 沿阶查找 → 逐级分裂 → 标记元数据 → 返回首页描述符。
释放数据流：`base + n` → 配对核对 → 清整块 → 逐级伙伴合并 → 计数恢复。

## 3. 数据结构设计

### 3.1 集中管理状态

```c
struct buddy_state {
    list_entry_t free_list[BUDDY_MAX_ORDER + 1];  /* 16 条按阶空闲链表头 */
    size_t nr_free;                               /* 空闲页总数（nr_free_pages 的答案） */
    size_t nr_managed;                            /* 已登记总页数（含已分配），供 check 对账 */
    struct buddy_page_meta meta[BUDDY_MAX_PAGES]; /* 32768 项逐页私有元数据 */
    uint8_t seen[BUDDY_MAX_PAGES];                /* 结构检查专用覆盖位图 */
};
```

元数据每页 2 字节（`state` 一字节 + `order` 一字节）。整个状态在当前 RISC-V ELF 中占 `0x18110`，即 98576 字节，约占 128 MiB DRAM 的 0.07%。

### 3.2 五种页状态

| 页状态                          | 元数据 | 描述符标志          | `property` 字段 |
| ------------------------------- | ------ | ------------------- | --------------- |
| 未登记页 `BUDDY_UNMANAGED`      | —      | （保留区页）        | —               |
| 空闲块首页 `BUDDY_FREE_HEAD`    | 阶数 k | `PageProperty` 置位 | 实际块长 `2^k`  |
| 空闲块内部页 `BUDDY_FREE_TAIL`  | 0      | 无                  | 0               |
| 分配块首页 `BUDDY_ALLOC_HEAD`   | 阶数 k | 无                  | 原始请求 `n`    |
| 分配块内部页 `BUDDY_ALLOC_TAIL` | 0      | 无                  | 0               |

`property` 在空闲首页存块长、在分配首页存原始 `n`：同一页任一时刻只处于其中一种状态，两者不冲突。分配首页的"原始 `n` + 元数据实际阶数"共同构成释放时的配对核对依据。

### 3.3 关键设计决策与理由

| #   | 决策项        | 选择                         | 理由                                                                                                            | 放弃的替代方案                                                                    |
| --- | ------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1   | 空闲块组织    | 16 条按阶链表                | 每阶内块等长，定位后摘除/插入 O(1)；阶数固定 16，查找最多扫 16 条链表头；不需要动态内存                         | 平衡树（需额外节点存储与维护成本）、按阶位图（查找需位扫描）                      |
| 2   | 页级信息存放  | 独立 `meta[]` 数组（2 B/页） | "空闲块阶数"与"分配记录（原始 n + 实际阶）"是两组正交信息；独立数组可被结构检查单独核对；不动公共 `struct Page` | 全部塞进 `property`/`flags`（语义过载；框架仅约定空闲首页的 `PageProperty` 语义） |
| 3   | 存储时机      | 编译期静态固定容量           | `init()` 时无任何分配服务可用；容量上界 = 128 MiB / 4 KiB = 32768 项，固定且可断言                              | 运行时动态分配（初始化顺序上不可能）                                              |
| 4   | `seen[]` 位置 | 静态数组                     | 32768 字节的覆盖位图，小容量内核栈放不下                                                                        | 栈上数组（爆栈风险）                                                              |
| 5   | 伙伴定位      | 相对索引 XOR                 | O(1) 求伙伴；配合 `nbase` 对齐断言，相对对齐与物理对齐等价                                                      | 直接物理地址运算（需额外处理基址偏移）                                            |

## 4. 伙伴定位与对齐基准

- 页索引定义：`i = page - pages`，基准是 `pages[0]` 对应的 `DRAM_BASE = 0x80000000`，不是第一个空闲页
- 阶 `k` 块的首页满足 `i mod 2^k == 0`
- 伙伴公式：`buddy_index = i ^ (1 << k)`——把阶 `k` 对应的二进制位取反，一步定位
- `buddy_init()` 断言 `nbase`（DRAM 起始页号）按最大块页数 32768 对齐，因此"相对索引对齐"与"物理地址对齐"等价
- 安全顺序：先用 `buddy_in_range()` 验证伙伴索引与完整块范围都在管理界内，再访问其元数据；仅"同阶、空闲、已登记"的首页可参与合并

## 5. 核心算法设计

### 5.1 `init()`（buddy_init）

`memset` 清零整个集中状态；逐条初始化 16 条链表；断言 `nbase` 对齐。不访问任何页描述符——此时 `page_init()` 尚未执行。

### 5.2 `init_memmap(base, n)`（登记与拆分）

1. 验证：`base` 索引与 `n` 在管理界内；本段每页当前必须是 `PageReserved` 且 `BUDDY_UNMANAGED`（防止重复登记或把非保留区当空闲区登记）
2. 清理：清除保留标志、引用计数与旧 `property`，整段先标记为 `BUDDY_FREE_TAIL`
3. 贪心拆分：从段起点开始，每轮取"当前索引对齐且不超过剩余长度"的最大二次幂块，插入对应阶链表（插入时顺带尝试伙伴合并），索引前移、剩余递减
4. 计数：`nr_free += n`、`nr_managed += n`，恰好登记 `n` 页，不丢弃尾页

性质：不规则起点、非二次幂长度、多段、乱序交付的合法区域均正确处理——凑不满一大块的尾页保留为低阶小块而不是丢弃；相邻已登记段可以合并，但绝不跨过未登记页或保留区。

### 5.3 `alloc_pages(n)`（取整与分裂）

```text
n == 0 或 n > 32768        → NULL（先查范围再移位，杜绝溢出）
k = 使 2^k ≥ n 的最小阶
2^k > nr_free              → NULL（状态不变）
从阶 k 到 15 找第一条非空链表 → 全空则 NULL
取出块首页，从 found 阶逐级分裂到 k 阶：
    每次把右半块（index + 2^found）挂回 found-1 阶链表，继续分裂左半
整块标 BUDDY_ALLOC_TAIL；首页标 BUDDY_ALLOC_HEAD、meta.order = k、property = n
nr_free -= 2^k，返回首页描述符
```

不清零返回的内存、不触碰存活块数据；所有失败分支都在任何状态修改之前返回。

### 5.4 `free_pages(base, n)`（回收与合并）

1. 配对核对：`n` 能通过同一取整检查；`base` 是本分配器返回的 `BUDDY_ALLOC_HEAD` 首页；`meta.order` 与重算阶数一致且 `property == n`——三条全部满足才接受，拦截错页、错大小、重复释放
2. 清整块：所有页重置为 `BUDDY_FREE_TAIL`，清标志、引用计数与 `property`；`nr_free += 2^k`（只加这一次）
3. 逐级合并（`buddy_insert_free` 循环）：

```text
cur = k
循环（cur < 15）：
    other = index ^ 2^cur
    若 other 出界 / 非 BUDDY_FREE_HEAD / 阶数 ≠ cur → 停止
    摘出 other；合并块取 min(index, other) 作新首页；cur++
最终把块挂入 cur 阶链表
```

合并只发生在"真正伙伴"之间：地址相邻但不是伙伴、伙伴被占用、伙伴未登记，均不合并；合并不额外增加页数。

### 5.5 失败不变性

非法 `n`、容量不足、无可用阶块等所有失败路径都不修改管理状态。测试 Case 6 以"失败前后空闲计数、只读状态摘要、存活数据逐一比对"验证了该性质。

## 6. 与内核框架的集成

### 6.1 管理器注册

```c
const struct pmm_manager buddy_pmm_manager = {
    .name = "buddy_pmm_manager",
    .init = buddy_init,               .init_memmap = buddy_init_memmap,
    .alloc_pages = buddy_alloc_pages, .free_pages = buddy_free_pages,
    .nr_free_pages = buddy_nr_free_pages, .check = buddy_check,
};
```

`buddy_check()`：先做结构自检；`PMM_USE_BUDDY` 下接着运行 `buddy_test()` 八组用例，最后再次结构自检，确认测试没有破坏管理状态。

### 6.2 条件编译与构建切换

- `pmm.c` 的 `init_pmm_manager()`：定义 `PMM_USE_BUDDY` 时选择 `buddy_pmm_manager`，否则保持 `best_fit_pmm_manager`
- 宏经 Makefile 现有 `DEFS` 传递：`make DEFS=-DPMM_USE_BUDDY`
- 每次配置切换前 `make clean`，防止旧对象文件掩盖配置变化
- 默认（Best-Fit）构建中，链接器垃圾回收移除未被引用的 Buddy 符号——已用符号表核对默认 ELF 不含 Buddy 状态或回调符号

### 6.3 与 SLUB 的兼容

SLUB 以 `alloc_pages(n)` 取得连续页、按同一原始 `n` 调用 `free_pages(base, n)` 归还。Buddy 通过"分配首页 `property` 保存原始 `n` + 释放时配对核对"直接支持这一用法。SLUB 的对象元数据写在物理页内的对象存储区，Buddy 的管理信息写在页描述符与独立静态数组中，二者空间互不覆盖。

## 7. 复杂度与空间开销

| 项              | 结果                            | 说明                                                 |
| --------------- | ------------------------------- | ---------------------------------------------------- |
| 一次分配 / 释放 | `O(2^k + 16)`                   | 逐页元数据处理 `2^k` 项 + 阶数扫描 / 合并循环上限 16 |
| 查找空闲块      | 最多扫 16 条链表头              | 每阶非空判断 O(1)                                    |
| 管理空间        | 98576 字节静态                  | `meta` 65536 B + `seen` 32768 B + 链表与计数约 272 B |
| 内部碎片        | 最坏浪费 `2^k − n < 2^(k-1)` 页 | 向上取整的固有代价，属接口契约选择                   |

## 8. 测试与验证策略

### 8.1 测试目标与总体安排

测试要回答三个问题：六个回调的行为是否符合 1.4 节契约；分配器内部结构是否始终自洽；失败路径是否真正做到"不改变状态"。验证分两阶段：

1. **接入自检（第一阶段）**：干净构建并确认 `-DPMM_USE_BUDDY` 真正生效；QEMU 启动输出 `memory management: buddy_pmm_manager`，确认没有回落到 Best-Fit；运行结构自检——不依赖具体申请序列，直接核对内部不变量。
2. **独立行为测试（第二阶段）**：新增 `buddy_test.c`，实现 `void buddy_test(void)`，由 `buddy_check()` 在结构自检之后调用，八组用例跑完后再做一次结构自检，确认测试本身没有破坏管理状态。

测试遵循五条原则：以公开接口（`alloc_pages`/`free_pages`/`nr_free_pages`）的黑盒行为为主、结构检查为辅；期望值由**独立 oracle** 推导，绝不拿被测实现的内部状态充当判据；场景**确定性**（固定区域布局、固定随机种子），失败可复现；每条断言可定位（用例号/轮次/步号）；未覆盖场景**如实声明**，不计入通过。

### 8.2 测试隔离机制设计

内核真实分配器的状态由启动流程决定、且被后续服务依赖，不能直接摆布；而把算法复制一份到测试文件里改着测，测的就不是生产代码。本设计用三个机制解决这一矛盾：

**机制一：状态指针切换（换账本，不换算法）。** 全部算法函数通过 `buddy_active` 指针访问当前状态结构体：平时指向生产实例 `buddy_live`，测试期间切到空白实例 `buddy_test_state`，跑完切回。初始化、分配、释放及辅助函数共 13 个函数体与生产代码逐字一致（统一换行后比对，见完整性记录），因此被测对象就是内核实际运行的那份算法。

**机制二：64 页独占块（真实内存中的试验田）。** 需要真实页面的用例按以下流程获得安全场地：

```text
① 记录空闲页基线
② alloc_pages(64) 取得独占块；取不到则如实报 UNTESTED，不计入通过
③ 验证块属性（64 页对齐、ALLOC_HEAD、阶 6）
④ 静态备份全部 64 个页描述符，清零并标记保留
⑤ 切换到测试状态，从零初始化，按用例菜单登记子区域
⑥ 运行用例回调
⑦ 复核终态（登记数、空闲数、结构自检）
⑧ 按备份复原描述符，切回生产状态
⑨ 按原始 64 页整块归还，断言空闲页数 == 基线
```

**机制三：阶 15 静态描述符模型。** 128 MiB 里找不出干净的整块 32768 页，最大阶改用静态 `Page[32768]` 数组覆盖：临时把全局 `pages`/`npage` 指向假描述符，登记完整 32768 页后正常执行分配、拆分、合并的记账逻辑，不做物理地址转换或写入。既验证了最大阶行为，又不触碰真实内存。

两个隔离入口都有防呆断言：进入前必须处于生产态且未隔离，退出后必须恢复原状；任何一步不满足立即中止而不是带病继续。

### 8.3 通用测试骨架与判定机制

- **`CHECK` 宏**：所有断言带用例号、轮次、步号与源码位置，失败信息可直接定位到具体操作
- **`run_scope` + `scope_body` 骨架**：受控用例共用同一套流程——核对区域菜单合法（不越界、不重叠）→ 核对初始登记数 → 检查未登记页未被触碰 → 运行用例本体 → 统一清理（`release_all`）→ 断言容量恢复 → 再次检查未登记页与结构自检
- **静态记录数组**：`records[]` 记录存活分配，`registered[]`/`occupied[]` 位图记录登记与占用；容量明确，不依赖被测分配器或尚未初始化的 SLUB
- **状态指纹（digest）**：对活跃状态的关键字段（状态指针、全局变量、计数、各阶链表头、逐页元数据与描述符字段）做 FNV 式哈希，用于失败不变性比对——失败请求前后指纹必须一致
- **汇总规则**：每组用例 `report_case` 独立报告；只有全部必需组实际执行并通过，才打印 `8/8 required groups passed`

### 8.4 八组用例设计

| 用例                      | 场景构造                                                                                                                                                        | 判定内容                                                                                                      | 能发现的错误                                               |

### 8.5 随机对拍与独立位图 oracle

Case 8 的期望值不由被测分配器自己产生：测试侧维护独立的逐页位图（`registered`/`occupied`）。每次分配后核对返回块——落在已登记页上、页数为该阶的 `2^k`、按阶对齐、位图中原为空闲且块内无重叠——核对通过后才在位图中标记占用；释放按 `records[]` 中的原始配对核对后同步位图。每轮结束要求位图全空、空闲页数恢复、原始大块可再次整体取得。固定种子保证任何失败都可以原样重放定位。

### 8.6 通过判据与覆盖限制

**通过判据**（缺一不可）：启动输出确认管理器为 `buddy_pmm_manager`；八组必需用例全部实际执行且 PASS；入口空闲页基线在全部用例结束后恢复；无 panic 或明确 FAIL。QEMU 包装命令的超时退出码 124 只表示测试成功后内核继续空转被限时结束，不作为通过判据。

**覆盖限制（如实声明）**：阶 15 的真实 32768 页物理分配无法排除固件与内核保留区，只做描述符模型正向测试及真实内存中的预期失败，不声称对真实 128 MiB 块做过读写；高阶 6..14 的成功分配检查全部描述符及请求首尾数据，未逐字节扫描整个请求；随机部分仅一个固定种子的有限 4096 步；并发、非法指针、重复释放、部分释放不在所选契约内。上述通过是对所列场景的实验验证，不是对所有输入的形式化证明。

## 9. 已知局限与改进方向

1. **逐页元数据使分配 / 释放带 `O(2^k)` 项**：高阶大块的操作代价线性于页数。可改为仅首页元数据 + 块长推导，但会削弱释放时的整块核对强度；本实现优先可核对性
2. **内部碎片**：向上取整最坏浪费近半（如申请 `2^(k-1)+1` 页实占 `2^k` 页），是 Buddy 结构的固有代价
3. **单核串行假设**：未加锁；若支持 SMP 需为链表与计数补锁或 per-CPU 化
4. **静态容量**：`meta`/`seen` 按 128 MiB 上限固化，更大 DRAM 需同步扩容常量并重估空间占用
